# Optional Roast Mode

Read only when the user requests a roast or a blunt critique. The existing `prep-that-doc roast` invocation selects this mode without another installation. Review remains the default.

Use the same protection, evidence, classification, and author-authority rules as a review. Roast edits nothing. Include LOW candidates by running the detector with `--strict`, then judge them in context.

## What To Say

Lead with the strongest supported consequence for the reader. Describe recurring habits rather than repeating every instance. Explain any gap between the document's stated purpose and the information it supplies.

For example, a document titled "Cutover Plan" may list deployment commands but supply no verification gate. The useful criticism is that the operator cannot tell when to proceed, not that the document violates a preferred heading template.

Support criticism with locations and concrete examples. Group repeated instances when one explanation covers them. Keep missing facts as author questions and distinguish them from editable prose.

## Boundaries

- Critique the document, never the author's skill, effort, taste, or intelligence.
- Do not invent a finding, inflate severity, or count protected examples as defects to make the roast longer.
- Do not change files or guess at missing values because the user requested bluntness.
- A good document deserves a short, honest result, including when there is little to criticize.

Use the user's requested format. Otherwise give the reader consequence, recurring patterns, supporting findings, and a classified outcome when useful. A separate joke, rigid opening formula, or command at the end is unnecessary.
